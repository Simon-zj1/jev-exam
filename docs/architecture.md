# 架构与取舍

这份文档解释「为什么是这样设计的」，也是面试时最值得看的一页。

## 一句话定位

**把「判定」从一次模型调用，拆成一批可核对的原子问题。** 出题交给生成模型，判分交给决策模型，
控制流与合成交给代码；每个分数都能回到具体的得分点与原文出处。

## 系统边界

| 做 | 不做 |
| --- | --- |
| 把材料切成知识点、出题、拆评分点 | 解析 PDF / OCR / 抓网页（先要文本） |
| 客观题确定性判分、主观题逐点概率判定 | 数学计算与代码正确性判定（需要执行器） |
| 覆盖率与溯源审计、置信门控 | 自动复审低置信度题目（标记给人看） |
| 错题本、掌握度、额度、BYOK | 训练或微调模型 |

## 数据流

```
材料（纯文本/Markdown）
   │  ① 不可信数据扫描（提示注入/角色劫持/分隔符冲突）
   ▼
出题（生成式 LLM 或 Agent）
   │  产出 topics[] + questions[]（每题带 source_anchor，简答带 rubric_points[evidence_span]）
   ▼
落地校验  ── schema / 锚点可定位 / 近似去重 / 失败重试 ≤2 次后丢弃
   │
   ▼
溯源契约 + 覆盖率审计
   │  材料事实必须逐字可定位；没有被题目覆盖的要点如实列出
   ▼
学习者作答
   │
   ├── 客观题 → 确定性判分（归一化比对；仅填空的语义等价调用一次判定）
   └── 主观题 → 每个得分点一条 noul 问题（并行）→ 概率
                     │
                     ▼
              代码合成：Σ(weightᵢ × pᵢ)/Σweightᵢ − 0.3·P(矛盾) − 0.3·P(编造)
                     │
                     ▼
              置信门控：strength = |p − 0.5| × 2 < 0.5 → 整题「待复核」+ 分数区间 + 不计入掌握度
   ▼
报告（Web / 离线单文件 HTML）→ 错题本 → 掌握度
```

## 三个角色，不能混

| 环节 | 由谁负责 | 为什么不能换 |
| --- | --- | --- |
| 出题、拆点 | 生成式 LLM / Agent | Jev 不生成任何文字，做不了这件事 |
| 客观题判分 | 确定性代码 | 精确比对是免费的，也是唯一可复现的 |
| 主观题判分 | 决策模型（Jev） | 需要校准概率与置信度，而不是一段听起来合理的解释 |

## 判定链路的关键细节

1. **每个得分点一条问题，且问题自带它所判的那一点。** 并行问题只靠 key 区分是无效的——
   模型无法知道自己在判哪一点，质量会静默崩掉（这是开发中真实踩到的坑）。
2. **`noul` 没有 confidence 字段。** 因此用 `strength = |p − 0.5| × 2` 衡量判定强度，
   而不是假装它有置信度。
3. **并行采样 = 一次请求判全部得分点。** 一个主观题的所有 rubric 点是同一次请求里的多个问题，
   不产生多次网络往返。
4. **扣分在代码里，不在模型里。** 模型只给「矛盾」「编造」的概率，怎么扣由 `src/lib/config.ts` 决定。
5. **待复核不进掌握度。** 不确定的分数不能污染学习画像。

## 关键取舍（面试常问）

### 为什么不做成 Agent？

判定需要**可复现、可审计、便宜**。让模型自由规划、循环调用工具，会让同一个答案得到不同分数，
也会把成本推向不可控。所以这里的形态是 "AI-powered software"：代码拥有控制流，模型只做窄判断。
知道什么时候**不该**用 Agent，是这套设计的核心判断。

### 为什么不让 LLM 直接打 0–100 分？

因为那样得到的是一个不可核对的数字：没有置信度、不可复现、也无法解释为什么是 73 而不是 68。
拆成「每个得分点一条问题」之后，分数是概率的加权和，可以用 rubric 表逐行核对。

### 为什么自己写 CLI + MCP？

判定能力如果只能通过网页使用，就没法进 Agent 的工作流。`scripts/study.ts` 与
`scripts/mcp-server.ts` 让同一套实现既能在网页里跑，也能被 Codex / Claude Code 直接调用；
`SKILL.md` 提供任务级契约，`AGENTS.md` 约束别人改这个仓库时不要破坏契约。

### 为什么材料事实要单独建模？

因为模型会改写措辞。如果「题干」「参考答案」和「材料原文」混在一起，用户无法判断哪句话有依据。
所以只有 `source_anchor` 与 `evidence_span` 被允许代表材料事实，并且必须能逐字定位。

## 可核对的保证

| 保证 | 实现 | 验证 |
| --- | --- | --- |
| 材料事实可定位 | `src/lib/provenance.ts` | 单测 + 报告里的违规清单 |
| 覆盖率不假装完整 | `src/lib/coverage.ts` | 单测 + 报告里的未覆盖句子 |
| 不确定就标出来 | `src/lib/grading/subjective.ts` | 单测（低强度点触发待复核 + 分数区间） |

## 验证方式与真实数字

- **测试**：单元 + 集成 + HTTP 路由 + CLI 端到端 + MCP 协议 + PGlite 真库，共 60+ 用例。
- **判定评测**：金标准集（12 道主观题 / 42 个标注得分点）输出逐点准确率、Brier、校准分桶、
  自一致性；门槛是逐点准确率 ≥ 90% 且校准单调。
- **反例对照**：离线词面引擎在金标准集上 **71.4%** 逐点准确率、Brier **0.216**，校准分桶单调，
  但 12 道题里有 9 道判定强度不足被标为待复核——这个数字就是"词面重合不能替代校准模型"的证据。
- **示例产出**：`docs/demo/report.html`，覆盖 9/14，未覆盖的三句如实列出。

## 模块职责

```
src/lib/engine/       判定引擎（typesafe=Jev / llm-judge=基线 / lexical=离线演示），DecisionEngine 接口
src/lib/generator/    出题：LLM 出题器、离线出题器、落地校验（schema/锚点/去重/重试）
src/lib/grading/      判分：客观题确定性判分、主观题逐点合成与门控
src/lib/coverage.ts   覆盖率审计（哪些材料要点没被出题）
src/lib/provenance.ts 溯源契约（材料事实 vs 模型补充）
src/lib/security/     不可信材料扫描、分隔符转义、HTML 转义
src/lib/report.ts     离线 HTML / Markdown 报告渲染（支持品牌色与自定义 CSS）
src/lib/services/     业务服务层：材料、大纲、试卷、作答判定（逐题/一次性）、结果、错题、BYOK、额度
src/lib/db/           Drizzle schema + Store 接口 + Postgres / 内存两种实现
src/app/              Next.js 页面与 Route Handlers（含 /judge 与 /finalize 渐进判定）
scripts/study.ts      CLI：verify / grade / render / answer-template / demo
scripts/mcp-server.ts MCP server：verify_exam / answer_template / grade_answers / render_report
```

## 交付形态

| 形态 | 命令 | 适用 |
| --- | --- | --- |
| Web 应用 | `npm run dev` | 多用户、额度、错题本、掌握度 |
| Agent Skill | 装进 `~/.agents/skills/` 后说"用这份材料考我" | Codex / Claude Code 里的日常自测 |
| CLI | `npx jev-exam grade ...` | 脚本化、批处理、CI |
| MCP server | `npx jev-exam mcp` | 让 Agent 直接调用而不是拼 shell |

## 已知限制

- 金标准集只有 12 题，门槛还没在真实 Jev 上跑过（没有 key）；需要扩到 60–100 题。
- 覆盖率只说明"要点有没有出题"，不等于题目质量。
- Web 版认证是签名 Cookie，生产建议换 Supabase Auth + RLS。
- 不支持 PDF/OCR；材料必须是文本。
